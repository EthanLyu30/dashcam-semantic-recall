数据与检索PostgreSQL REAL[] 向量 + cosine_similarity 存储函数 / SQLite 降级 · 混合检索

关键设计 1 · 双引擎数据库

  • PostgreSQL：原生 REAL[] 向量列 + PL/pgSQL cosine_similarity()，库内排序
  • SQLite：JSON 向量 + numpy 余弦，零安装可演示
  • 9 张业务表对齐《概要设计 V4.0》第 4 章

关键设计 2 · 模型可降级

  • 默认 mock 确定性伪标签——离线演示不崩
  • 本机环境变量配 key 即走真 Qwen-VL 视觉理解
  • 调用失败指数退避重试，再失败回退 mock
  • 密钥只存本机环境变量，不入库、不进仓库

关键设计 3 · 事件聚合

  • 1 帧 / 6 秒抽样（可配），控制模型调用成本
  • 相邻 ≤10s 同类型帧合并为一个语义事件
  • 低置信事件自动进人工复核队列
  • 事件携带关键帧、标签、置信度、向量文本

实事求是：未完成与边界清单

不藏丑——每一条都写了原因和改进路径

⚠ 未达标 / 未验证（3 项）

  • 50 并发性能不达标：p95≈6.9s 超 4s 预算（实测数据，非估算）。瓶颈：单 worker + SQLite 写串行。改进：多 worker + PostgreSQL + 检索留痕异步化——属部署调优，非架构缺陷。
  • 部分性能指标未真机压测：2h/4K 预处理≤8min、回放跳转≤1s、启动≤2s。功能可用、体感流畅，但我们没有计时数据就不在表格里打勾。
  • Docker compose 未实跑验证：compose 文件与 Dockerfile 已编写并提交，但开发机未装 Docker，无法给出"亲测可用"的结论。

⚠ 有意取舍（课程范围外）

  • 异步任务队列（Celery/Redis）：演示场景同步处理已够用
  • 用户修改/禁用、自定义角色编辑：三固定角色已覆盖场景
  • HLS 流媒体、HTTPS 内建：部署期由反代提供

✅ 容易被当成"没做完"、实际已闭环的点

  • 管理页不是静态原型：11 页全部实时拉取后端、切页自动刷新
  • 界面上没有摆设按钮：所有操作按钮都接真实写接口并留审计；离线 Mock 模式会明示"离线模式"，不假装写入成功
  • mock 模型是显式声明的降级路径（README 有"真实跑通 vs mock"对照表），不是冒充真模型

质量保障

  • 86 个自动化测试全过：端到端、安全回归（流鉴权 / 上传上限 / JWT 策略 / RBAC 403）、召回质量、性能基准、24h 去重、批量失败隔离
  • 真实后端逐页截图走查 + 离线 Mock 全页面冒烟
  • API 契约文档逐端点标注"已实现 / 🔵 仅规划"，文档与代码同步审计过

总结与展望

结论

  • SRS 全部 9 项功能需求：8 项完整闭环，FR-09 主体完成（仅用户编辑/自定义角色未做）；复核、告警、报表等管理链路真实可用。

  • 全部结论可复验：86 个测试一条命令跑通，演示流程 10 步可现场重放，截图与库内数据一致。

若继续产品化（优先级排序）

  • ① 多 worker + PG + 异步写：解决 50 并发 p95
  • ② 异步任务队列：长视频后台处理 + 进度推送
  • ③ 用户管理补全（修改 / 禁用 / 自定义角色）
  • ④ HLS 流媒体 + HTTPS 端到端
